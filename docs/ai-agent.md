# Как использовался ИИ-агент

В задании сказано: описать требования, нарисовать диаграммы вариантов использования,
«скормить ИИ-агенту» и попытаться получить работоспособное решение на микросервисах.
Здесь честно описано, как это было сделано.

## Какой агент

Claude Code (в задании как пример назван opencode.ai, требования использовать именно его нет).
Агент работал на компьютере автора: сам создавал файлы, запускал Docker и тесты.

## Что было на входе

- Текст задания преподавателя.
- Тема «Автопарк» из списка примеров на портале: учёт машин и водителей по категориям,
  запрет вести несколько машин одновременно, обслуживание после каждой поездки только
  в будни с 8:00 до 17:00, запрет выпуска необслуженной машины, отчёты.

## Что сделал агент

1. Составил [REQUIREMENTS.md](../REQUIREMENTS.md) и диаграммы в `docs/diagrams`.
   Формулировки целей, рисков и критериев приёмки тоже подготовлены агентом.
2. По этим требованиям написал код пяти сервисов, веб-страницу, `docker-compose.yml`.
3. Написал модульные тесты правил и сквозной сценарий `scripts/check_requirements.py`,
   в котором каждая проверка подписана номером требования.
4. Запустил систему и прогнал проверки.

То есть весь код в репозитории сгенерирован ИИ-агентом. Автор репозитория — Ленец Е.

## Что пошло не так по ходу и как исправлено

| Проблема | Как обнаружена | Исправление |
|----------|----------------|-------------|
| PostgreSQL не стартовал: скрипт создания баз `init-databases.sh` не запускался из папки, подключённой с macOS («Permission denied») | `docker compose up` завершился ошибкой | Скрипт заменён на `init-databases.sql`, пароль читается командой `\getenv` |
| Шлюз считался «нездоровым», хотя работал | `docker compose ps` показал `unhealthy` | У шлюза не было адреса `/health`, по которому Docker проверяет сервис; добавлен |
| Проверка отчёта по водителю могла сработать раньше, чем до отчётов дойдёт событие | Разбор сценария до запуска | В сценарии добавлено ожидание нужного значения |

## Как убедиться, что результат работает

Доверять сгенерированному коду на слово нельзя (риск Р8 в требованиях), поэтому:

- 32 модульных теста проверяют правила отдельно от базы и сети;
- сквозной сценарий выполняет все критерии приёмки КП-1 … КП-13 на запущенной системе,
  включая остановку сервиса обслуживания «на ходу»;
- оба набора запускаются автоматически в GitHub Actions при каждой отправке кода.

Команды — в [README](../README.md).

## Наблюдения

- Агенту проще писать код, когда правила пронумерованы (БП-1 … БП-10): номера попали
  в комментарии, тесты и сообщения сценария, и по ним видно, что реализовано.
- Правило «только в будни с 8:00 до 17:00» нельзя проверить в произвольный день, если система
  берёт только текущее время. Поэтому в требования добавлено допущение: время события вводит
  сотрудник, но не из будущего.
- Агент сам не замечает ошибок окружения, пока не запустит код. Обе ошибки из таблицы выше
  нашлись только при реальном запуске.
